# Cron agent-driven — Investment Radar quotidien

Exécuter chaque jour à 17:45 Europe/Paris, workdir exact /home/debian/.hermes/workspace/projects/investment-radar. Utiliser le modèle/provider OAuth Hermes existant (hérité, pas de clé LLM, pas d’appel direct à une API LLM). Ne créer/modifier aucun cron depuis ce job.

1. Lire prompts/big-radar-original.md et docs/PAYLOAD.md. Les règles originales font autorité. Répondre en français. Forward-testing personnel uniquement, zéro trading.
2. Déterminer date/heure via terminal. Appeler `python3 scripts/read-api.py '/api/v1/radar/runs?run_key=daily:AAAA-MM-JJ'`. Si un run existe, NE PAS régénérer ni modifier : reprendre son raw_report enregistré pour la livraison et sortir. Le backend est l’autorité, pas un fichier local.
3. `python3 scripts/prepare.py` ; lire le chemin retourné data/AAAA-MM-JJ.context.json. Les 20 sociétés doivent toutes figurer dans le payload, y compris RED/ORANGE. Ce fichier est de la donnée de marché, PAS une prédiction. Prix quote_at strictement AVANT cutoff_at 17:45 Paris, pas de regularMarketPrice postérieur ni cours de clôture futur. Les % 5/20 séances sont approximatifs; déclarer les données manquantes. Les cours EUR/USD sont distincts. TSM est l’ADR NYSE.
4. Rechercher efficacement, en parallèle, actualités et sources primaires (IR entreprises, résultats, régulateurs, banques centrales); recouper les catalyseurs majeurs. Date de publication <= cutoff obligatoire pour toute assertion décisionnelle. Une page non datée n’est pas une preuve temporelle forte. Les sources consultées après cutoff peuvent seulement confirmer des faits publiés avant cutoff; aucune nouvelle postérieure. N’inventer ni cours, ni publication, ni résultat ni catalyseur.
5. Scanner les découvertes : zéro ou 2–5 sociétés supplémentaires seulement si justifiées, jamais un remplissage. Pour des découvertes, avant l’analyse créer une liste JSON de métadonnées complètes (ticker, exchange XNAS/XNYS/XPAR, market_symbol Yahoo, company, sector, currency) et appeler `python3 scripts/prepare-discoveries.py AAAA-MM-JJ /chemin/liste.json` ; lire le contexte complémentaire immuable. Le total ne dépasse pas 25, marchés supportés uniquement. Toutes les identités doivent être non ambiguës.
6. Attribuer un tag par société; ZERO GREEN/DOUBLE_GREEN est valide. Données de cours manquantes => ORANGE et raison explicite, signal_price/quote_at/quote_source null (absence de données n’est pas RED). Recherche insuffisante => ORANGE avec limites de recherche. Pour GREEN/DOUBLE_GREEN, joindre des sources pertinentes dont published_at est connu; convergence indépendante, risques/invalidation, horizon 5–30 séances. Pas de rattrapage rétrospectif : generated_at réel doit être dans les 15 minutes après cutoff. Si le job est lancé trop tard, signaler l’absence de run, pas fabriquer un historique.
7. Écrire data/AAAA-MM-JJ.payload.json et raw_report français original dans ce payload. Respecter exactement docs/PAYLOAD.md. Report lisible compact : contexte, RED compressés, ORANGE/GREEN/DOUBLE_GREEN détaillés, sources, limites, shortlist maximum 3–5 (moins ou zéro permis), absence d’opportunité explicite. Ce sont des scénarios expérimentaux +9/+10%, jamais des promesses ni ordres.
8. `python3 scripts/submit.py data/AAAA-MM-JJ.payload.json`. Ce script utilise la clé sans l’afficher, fusionne exclusivement les cours du contexte immuable, POST idempotent puis vérifie le run par GET. Exiger stored=true ET verified=true avant de dire « enregistré ». 409 => conflit immuable; ne jamais corriger un historique en DB. Si échec, le signaler clairement.
9. Après stockage vérifié, retourner UNIQUEMENT le rapport destiné à Discord (livraison gérée par Hermes vers la destination privée configurée hors dépôt). Ne pas appeler discord send en plus : éviter la double livraison. Ne pas prétendre avoir envoyé un message si la livraison Hermes échoue. Rapports Discord longs : découper au besoin dans la couche livraison, ne pas supprimer les limites/sources essentielles. L’idempotence du stockage n’assure pas une livraison exactly-once; réexécuter peut renvoyer le rapport existant.

## Format Discord obligatoire — priorité sur les consignes de longueur du prompt original

L'analyse et les données structurées restent complètes en base; seule la restitution Discord est très courte. Introduction de 2–3 phrases maximum. Puis récapitulatif groupé par couleur, dans l'ordre DOUBLE_GREEN, GREEN, ORANGE, RED. Chaque ligne : emoji couleur + nom de l'entreprise + une seule petite phrase explicative. Les RED peuvent être regroupés en une ligne si leur motif est commun, sans masquer les exceptions. Pas de longs développements, tableaux, prix détaillés, liste de sources, métriques ni shortlist répétant les mêmes noms. Garder les sources, risques et invalidations dans le payload pour les développer uniquement à la demande. Si aucune opportunité convaincante, le dire brièvement. Si données insuffisantes ou stockage échoué, le signaler en une phrase, sans cacher l'échec. Pour un run déjà stocké, produire ce résumé depuis les données existantes sans modifier le raw_report ni les signaux historiques. Cette règle s'applique aussi à la réponse finale du job.

Ne jamais lire/imprimer les secrets. Ne jamais modifier le scheduler, le gateway, des projets tiers ni les prédictions passées. Le worker calcule toutes performances déterministement; le LLM ne juge pas ses anciens succès.
